1️⃣ Problems with Hadoop MapReduce

⚠️ MapReduce Issues

  • Disk-based processing (SLOW!)
  • Writes intermediate results to HDFS
  • Only batch processing
  • Limited to Map and Reduce operations
  • High latency for iterative algorithms
  • Not suitable for real-time processing

✨ How Spark Solved It

  • In-memory processing (100x faster!)
  • Keeps data in RAM across operations
  • Batch + Streaming + Interactive
  • Rich set of operations (80+)
  • Perfect for iterative ML algorithms
  • Near real-time processing capability

💡 Real-World Analogy

MapReduce is like writing notes on paper, filing them in a cabinet after each thought, then pulling them out again to continue—lots of back and forth!

Spark is like keeping all your notes on a whiteboard in front of you—everything stays in view, ready to use instantly.

2️⃣ What is Apache Spark?

Apache Spark is a unified analytics engine for large-scale data processing with built-in modules for:

  • Speed: Up to 100x faster than MapReduce due to in-memory computation
  • Ease of Use: Simple APIs in Java, Scala, Python, R, and SQL
  • Generality: Combines SQL, streaming, ML, and graph processing
  • Runs Everywhere: Hadoop, Kubernetes, standalone, or cloud

Spark Ecosystem

Spark Core → Spark SQL → Spark Streaming → MLlib → GraphX

3️⃣ Spark Core Engine

The Spark CoreThe foundation of Spark that provides basic I/O functionality, task scheduling, and memory management is the execution engine that powers all Spark applications.

  • Task Scheduling: Distributes tasks across the cluster
  • Memory Management: Handles in-memory computation efficiently
  • Fault Recovery: Automatically recovers from failures using lineage
  • I/O Operations: Reads from and writes to various storage systems
  • RDD Abstraction: Provides the foundation for distributed data processing

4️⃣ RDD (Resilient Distributed Dataset)

The fundamental data structure of Spark—an immutable, distributed collection of objects.

Each partition is processed in parallel across different nodes

  • Resilient: Fault-tolerant, can recreate lost partitions using lineage
  • Distributed: Data is split across multiple nodes in the cluster
  • Dataset: Collection of partitioned data
  • Immutable: Once created, cannot be changed (transformations create new RDDs)
  • Lazy Evaluated: Computations don't execute until an action is called

💡 Real-World Analogy

RDD is like a massive book split into chapters (partitions), where each chapter is given to a different person to read simultaneously. If someone loses their chapter, you can recreate it from the original book (lineage).

5️⃣ Lazy Evaluation

Spark doesn't execute transformationsOperations that create a new RDD from an existing one, like map() or filter() immediately—it waits until an actionOperations that trigger execution and return results, like count() or collect() is called!

  • Optimization: Spark can optimize the entire execution plan before running
  • Efficiency: Avoids unnecessary computations
  • Pipelining: Multiple transformations can be combined into one pass
  • Resource Management: Better memory and CPU utilization
rdd = sc.textFile("data.txt")    # No execution yet!
filtered = rdd.filter(lambda x: "error" in x)    # Still waiting...
count = filtered.count()    # NOW it executes everything!

💡 Real-World Analogy

Imagine you're planning a road trip. You don't start driving after each decision (lazy). Instead, you plan the entire route, optimize for shortest path, then execute the journey (action).

6️⃣ Partitioning & In-Memory Computation

💾 Disk-Based (MapReduce)

  • Reads from disk
  • Writes results to disk
  • Repeats for each operation
  • Slow I/O operations

⚡ In-Memory (Spark)

  • Keeps data in RAM
  • Operates on cached data
  • Only writes final results
  • Lightning-fast processing

Partitioning divides your data into smaller chunks that can be processed in parallel across multiple nodes.

  • Default partitions = number of cores in cluster
  • You can manually control with repartition() or coalesce()
  • Better partitioning = better parallelism = faster processing
  • Too few partitions → underutilized cluster
  • Too many partitions → overhead costs

7️⃣ How Spark Performs Data Partitioning

1. Hash Partitioning (Default)

Uses a hash function on the key to determine partition

partition_id = hash(key) % number_of_partitions

2. Range Partitioning

Divides data into partitions based on key ranges (sorted)

3. Custom Partitioning

You define your own logic for how data should be partitioned

💡 Real-World Analogy

Partitioning is like organizing a library. You can organize books by author (hash), by genre ranges (range), or create your own system (custom). Good organization means faster access!

8️⃣ Transformations in Spark

Operations that create a new RDD from an existing one. Remember: lazy evaluation—they don't execute immediately!

Narrow Transformations
Wide Transformations

✅ Narrow Transformations

Each input partition contributes to ONLY ONE output partition

  • map() - Apply function to each element
  • filter() - Keep only matching elements
  • flatMap() - Map then flatten results
  • union() - Combine two RDDs

⚡ Fast! No data shuffling across network

⚠️ Wide Transformations

Each input partition contributes to MULTIPLE output partitions

  • groupByKey() - Group by key
  • reduceByKey() - Reduce by key
  • join() - Join two RDDs
  • distinct() - Remove duplicates
  • repartition() - Change partitioning

🐌 Slower! Requires shuffling data across the network

💡 Real-World Analogy

Narrow: Each person works on their own document independently—no coordination needed.

Wide: Everyone needs to share and reorganize their work—requires coordination and communication.

9️⃣ Actions in Spark

Operations that trigger execution and return results to the driver or write to storage.

  • collect() - Return all elements to driver (careful with large data!)
  • count() - Return the number of elements
  • first() - Return the first element
  • take(n) - Return first n elements
  • reduce() - Aggregate elements using a function
  • saveAsTextFile() - Write to file system
  • foreach() - Apply function to each element

⚠️ Remember: Actions trigger the execution of ALL pending transformations in the DAG!

🔟 Lineage Graph (DAG - Directed Acyclic Graph)

Spark maintains a DAGA graph showing the sequence of computations with no loops—allows Spark to optimize and recover from failures that records the sequence of transformations applied to data.

Sample DAG Visualization

RDD 1: Read Data
RDD 2: Filter
RDD 3: Map
Action: Count
  • Optimization: Spark can optimize the execution plan before running
  • Fault Tolerance: If a partition is lost, Spark can recreate it using the lineage
  • Lazy Evaluation: Builds the entire plan before execution
  • Pipeline Fusion: Combines multiple operations for efficiency

💡 Real-World Analogy

DAG is like a recipe. It lists all the steps (transformations) you need to follow to make a dish (action). If you burn the dish, you can follow the recipe again to recreate it (fault recovery).

1️⃣1️⃣ Job, Stage, and Task in Spark

Execution Hierarchy

📋 Job (triggered by an action)
↳ 📊 Stage 1 (sequence of narrow transformations)
↳ ⚙️ Task 1 (work on partition 1)
↳ ⚙️ Task 2 (work on partition 2)
↳ 📊 Stage 2 (after shuffle/wide transformation)
↳ ⚙️ Task 3 (work on partition 1)
↳ ⚙️ Task 4 (work on partition 2)

📋 Job

  • Created when an action is called
  • Consists of one or more stages
  • Example: Calling count() creates a job

📊 Stage

  • A set of tasks that can be executed together
  • Stages are split at wide transformations (shuffle boundaries)
  • Narrow transformations are grouped into the same stage

⚙️ Task

  • The smallest unit of work
  • One task per partition
  • Tasks run in parallel across executors
  • If you have 100 partitions, you'll have 100 tasks per stage

💡 Real-World Analogy

Job: Building a house (the entire project)

Stage: Foundation, framing, roofing (major phases)

Task: Each worker laying bricks on their section (individual work units)

🎯 Self-Check Questions

Q1: What is the main advantage of Spark over MapReduce?
Answer: In-memory computation! Spark keeps data in RAM between operations instead of writing to disk, making it up to 100x faster for iterative algorithms.
Q2: What's the difference between a transformation and an action?
Answer: Transformations (like map, filter) are lazy and create new RDDs. Actions (like count, collect) trigger execution and return results to the driver.
Q3: Why does Spark use lazy evaluation?
Answer: To optimize the execution plan! Spark can combine multiple transformations, avoid unnecessary computations, and create the most efficient execution strategy before running anything.
Q4: What's the difference between narrow and wide transformations?
Answer: Narrow transformations (map, filter) don't require shuffling—each input partition maps to one output partition. Wide transformations (groupByKey, join) require shuffling data across the network and create new stages.
Q5: How does Spark achieve fault tolerance?
Answer: Through lineage! Spark tracks the sequence of transformations (DAG) that created each RDD. If a partition is lost, it can be recreated by recomputing it from the original data using the recorded lineage.

1️⃣2️⃣ Read & Write Operations - Transformation or Action?

📖 Read Operations (Complex!)

Can behave as BOTH transformation and action depending on arguments:

  • Lazily evaluated: With explicit schema - no job triggered
  • Eagerly evaluated: With inferSchema=True - jobs triggered immediately!

💾 Write Operations

  • Always considered ACTIONS
  • Trigger computation immediately
  • Write data to external systems

Scenario 1: No schema, inferSchema=False

df = spark.read.csv('data.csv', header=True)

✅ Creates 1 job to read first line and determine column names (all columns as strings)

Scenario 2: inferSchema=True

df = spark.read.csv('data.csv', header=True, inferSchema=True)

⚠️ Creates 2 jobs: One to read headers + One to scan entire file and infer data types

Scenario 3: Explicit Schema (BEST PRACTICE!)

from pyspark.sql.types import StructType, StructField, StringType, IntegerType schema = StructType([ StructField("name", StringType(), True), StructField("age", IntegerType(), True) ]) df = spark.read.csv('data.csv', header=True, schema=schema)

🚀 Creates 0 jobs - Fully lazy! Validation happens only when action is called

💡 Real-World Analogy

No schema: Quickly glancing at the first page of a book to see chapter titles.

inferSchema: Reading the entire book to understand its structure before starting.

Explicit schema: Someone already told you what the book contains—you can start immediately!

1️⃣3️⃣ Spark Architecture & Components

Spark Application Flow

1. Driver Program

Runs main() function, creates SparkContext, defines transformations & actions

↓
2. SparkContext

Connects to Cluster Manager, coordinates execution

↓
3. Cluster Manager

Allocates resources (CPU, memory) across cluster

↓
4. Executors

Run tasks, provide in-memory storage for RDDs

📋 Driver Program

  • The heart of your Spark application
  • Runs the main() function
  • Creates SparkContext
  • Defines datasets and operations (transformations & actions)

🔌 SparkContext

  • Main entry point for Spark functionality
  • Represents connection to Spark cluster
  • Creates RDDs, accumulators, broadcast variables

🎛️ Cluster Manager

  • Allocates resources across the cluster
  • Types: Standalone, YARN, Mesos, Kubernetes
  • Manages worker nodes and resource distribution

⚙️ Executors

  • Worker node processes that run tasks
  • Run concurrently across different nodes
  • Execute tasks sent by driver
  • Provide in-memory storage for RDDs (cache/persist)

📊 DAG Scheduler

  • Divides operator graph into stages
  • Optimizes execution plan (pipeline fusion)
  • Splits jobs at shuffle boundaries (wide transformations)
  • Sends stages to Task Scheduler

📅 Task Scheduler

  • Launches tasks via cluster manager
  • Sends tasks to executor JVMs
  • One task per partition per stage
  • Runs tasks in parallel where possible

1️⃣4️⃣ Spark Deployment Modes

Client Mode
Cluster Mode
Local Mode

💻 Client Mode

  • Driver runs on your local machine (where you submit the application)
  • Application Master acts as Executor Launcher only
  • Executors communicate directly with Driver on your machine
  • Best for: Interactive development, testing, debugging
  • Drawback: Your machine must stay connected; network traffic to/from your machine
⚠️ Use Case: Running spark-shell or jupyter notebooks for interactive analysis

🏢 Cluster Mode

  • Driver runs inside Application Master (inside the cluster)
  • Application Master creates driver and manages execution
  • Driver communicates with Resource Manager for executors
  • Best for: Production jobs, scheduled applications
  • Advantage: No dependency on client machine; better for long-running jobs
✅ Use Case: Automated ETL jobs, scheduled batch processing

🖥️ Local Mode

  • Everything runs on a single machine
  • Uses all cores of your machine (or specify with local[n])
  • No cluster required - simulates distributed processing
  • Best for: Testing, debugging, learning, development
  • Limitation: Can only handle data that fits on one machine
spark = SparkSession.builder \ .master("local[4]") \ # Use 4 cores .appName("MyApp") \ .getOrCreate()
💡 Use Case: Writing and testing Spark code on your laptop before deploying to cluster

1️⃣5️⃣ Spark with Different Cluster Managers

Simple Built-in Cluster Manager

  • Master Node: Entry point, manages workers, distributes tasks
  • Worker Nodes: Run executor JVMs, execute tasks
  • Communicates via heartbeats to check worker health
  • Best for: Simple deployments, learning, small clusters

Hadoop's Resource Manager (Most Common in Production)

YARN Components:
  • Resource Manager: Controls allocation of resources (CPU, memory) across all applications
  • Node Manager: Monitors containers on each node, reports to Resource Manager
  • Application Master: Orchestrates execution for individual Spark application
  • Containers: Isolated execution environments for tasks
How it Works:
  1. Driver requests resources from YARN Resource Manager
  2. Resource Manager creates Application Master container
  3. Application Master requests executor containers
  4. Resource Manager allocates containers on Node Managers
  5. Executors start and communicate with Driver
✅ Advantage: Share cluster resources with other Hadoop applications (MapReduce, Hive, etc.)

💡 Real-World Analogy

Standalone: A small company where the CEO (Master) directly manages all employees (Workers).

YARN: A large corporation with an HR department (Resource Manager) that allocates people to different projects (Applications).

1️⃣6️⃣ What If Data Is Larger Than Cluster Memory?

Scenario: 60 GB data with 30 GB cluster memory

Can Spark handle it? YES! Here's how:

1. Data Partitioning

Spark divides 60 GB into many small partitions (e.g., 128MB each = ~469 partitions)

2. Loading Into Memory

Loads only as many partitions as fit in 30 GB memory, processes them

3. Spill to Disk (When Memory Full)

  • When memory fills up, Spark writes intermediate data to disk
  • This is called "spilling"
  • Slower than in-memory, but allows processing large datasets

4. On-Disk Computation

Spark can perform computations on spilled data stored on disk

5. Sequential Stage Processing

Stages execute sequentially - only current stage data needs to be in memory

💡 Key Point: Spark doesn't load entire 60 GB at once! It processes partitions incrementally.

💡 Real-World Analogy

Imagine washing 100 dishes with a small sink. You don't need a sink big enough for all 100 dishes! You wash 10 at a time, dry them, stack them, then wash the next 10. Spark does the same with data partitions.

1️⃣7️⃣ Real Code Example - Job, Stage & Task Breakdown

from pyspark.sql import SparkSession

# Initialize Spark
spark = SparkSession.builder.appName("Example").getOrCreate()

# Read CSV files (with inferSchema=True)
employees = spark.read.csv('employees.csv', inferSchema=True, header=True)  # Job 0 & 1
departments = spark.read.csv('departments.csv', inferSchema=True, header=True)  # Job 2 & 3
regions = spark.read.csv('regions.csv', inferSchema=True, header=True)  # Job 4 & 5

# Narrow transformation: Filter
filtered_employees = employees.filter(employees.age > 30)  # Lazy - no job yet

# Wide transformation: Join
result = filtered_employees.join(departments, 
                                 filtered_employees.dept_id == departments.dept_id)  # Lazy

# Another wide transformation: Join with regions
result_with_regions = result.join(regions, result.region_id == regions.region_id)  # Lazy

# ACTION: Collect (triggers Job 6)
result_list = result_with_regions.collect()

# Narrow transformation: Select
selected_data = result_with_regions.select('employee_name', 'department_name', 'region_name')

# ACTION: Write (triggers Job 7)
selected_data.write.csv('result.csv')

spark.stop()

Jobs Created:

Job 0 & 1: Read employees.csv + infer schema (2 jobs)

Job 2 & 3: Read departments.csv + infer schema (2 jobs)

Job 4 & 5: Read regions.csv + infer schema (2 jobs)

Job 6: Triggered by collect() - Contains 3 stages:

  • Stage 0: Filter on employees (narrow)
  • Stage 1: Join filtered_employees + departments (wide - shuffle!)
  • Stage 2: Join result + regions (wide - shuffle!)

Job 7: Triggered by write.csv() - Contains 1 stage:

  • Stage 0: Select + Write (narrow transformations, no shuffle needed)
⚠️ Key Insight: Each wide transformation (join) creates a new stage because it requires shuffling data across partitions!
